缓存失效之后：一次关于
“新鲜感”的系统思考

一个缓存 key 没有失效，整个首页却像失去了记忆。从一次线上事故出发，聊聊缓存、认知，以及我们为什么总会忘记更新。

事故报告里写着“缓存正常”。但用户看到的首页，仍然停留在三天前。我们花了很久才承认：失效的不是缓存，是我们对“新鲜”的默认假设。

TL;DR

缓存解决的是读取速度，不是内容新鲜度。新鲜度需要一个明确的负责人、一个可观测的过期信号，以及一次在事故之后仍然会被执行的更新动作。

01一次没有报错的故障

那天下午，监控没有红色。首页的缓存命中率是 99.7%，CDN 边缘节点一切正常，接口的 P99 甚至比平时还低了一点。直到有人在群里发了一张截图：首页最新的一篇文章，日期停在三天前。

我们第一反应是查缓存。Redis 里的 key 还在，TTL 还剩十几个小时，内容服务的版本号也没有变。所有指标都指向同一个结论：系统运行良好。可用户看到的内容，确实是旧的。

我们以为自己在缓存数据，其实是在缓存一个已经不再成立的判断。

— 事故复盘笔记

问题不在 Redis，也不在 CDN。问题在于，发布文章的链路里有一个环节仍然从旧快照读取数据；它成功了，所以没有报警。它返回了 200，所以监控认为一切正常。我们把“请求成功”误当成了“内容新鲜”。

02新鲜感不是默认存在的

缓存只是把一次计算结果复制到更近的地方。它让读取更快，但不会替我们确认：这份结果是否仍然代表现在。大多数缓存事故都不是缓存挂了，而是缓存还活着，世界已经变了。

最典型的写法通常长这样：

typescript 
const cached = await cache.get(key);
if (cached) return cached;

const next = await refresh(key);
await cache.set(key, next, ttl);
return next;

这段代码没有错。它只回答了一个问题：“有没有缓存？”它没有回答：“缓存还代不代表现在？”

于是我们开始把“新鲜度”拆成三个可以回答的问题：

  • 谁负责让这份缓存失效？是一个发布动作，一个定时任务，还是某个人的记忆？
  • 失效之后，谁负责重建？重建失败时，用户看到什么？
  • 如果没有人发现它过期了，系统里有没有一个信号会替我们发现？

这三个问题听起来像管理问题，最后都会落成工程问题。没有负责人的缓存，本质上是一份没有过期日的承诺。

03给“新鲜”找一个负责人

事故之后，我们做了一件很小的事：给每一个缓存对象写一个负责人，以及一个可以被验证的过期信号。没有引入新的中间件，也没有重写缓存层，只是把原本藏在代码里的假设，搬到了一张所有人都能看见的表上。

缓存对象过期信号负责人失败时
首页文章列表发布 / 编辑 / 删除内容服务回源，并降级为短 TTL
文章详情正文或标题更新内容服务显示旧版本并标注
站点统计每日凌晨重构数据任务隐藏数字，不显示 0

表写出来之后，争论反而变少了。因为很多“缓存策略”的讨论，最后都变成了“谁在什么时候负责让它变新”的讨论。技术方案没有变复杂，变化的是责任被写了下来。

可观测性也不是多接一块大屏。它更像是提前想清楚：当内容变旧时，哪个指标会先变？我们最后加了一个很朴素的检查：每次发布后，比较源站版本号和边缘缓存版本号，不一致就记录一条 warn。它不漂亮，但在下一次发布时救了我们一次。

04事故之后

现在再看那次事故，它更像一次提醒：系统里最危险的东西，往往不是会报错的组件，而是那些“看起来还在正常工作”的假设。

缓存可以让我们更快地看到旧世界，但不能替我们决定世界是否已经更新。新鲜感不是默认存在的，它需要被设计、被负责、被观察。

写代码，也写下为什么。下一次再遇到类似的问题，我希望我们先问的不是“缓存怎么没失效”，而是“我们凭什么认为它应该失效”。

1 这里讨论的是内容型缓存；交易、库存等强一致场景需要另一套约束。技术方案会变，但“谁负责让它变新”这个问题不会消失。

∎
